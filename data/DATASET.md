# Synthetic dataset — TBX finance assistant

Generated by `../generate_dataset.py` (seed `20260905`, stdlib only). Re-running it
reproduces these files byte for byte.

```
python3 generate_dataset.py                       # 100,000 transactions (default)
python3 generate_dataset.py --transactions 500000 # bigger
python3 generate_dataset.py --dirty               # add the defective rows (see below)
```

### 2. The vendor-name collision trap

Nine counterparties contain the string `SELECT`, and they are **not the same business**:

`SELECTION ELECTRONICS`, `SELECTION MOBILE`, `NAVYUG SELECTION`, `SELECTIONMALIGAI`,
`UMANG SELECTION`, `SELECT MOBILES`, `SELECTRICITY ONE PRIVATE LIMITED`,
`SELECTRICITY TWO PRIVATE LIMITED`.

On top of that, `SELECT CITY SAKET DELHI` and `SELECT CITYWALK DELHI` are **shopping mall
names in the location suffix**, attached to 2,400-odd transactions with completely
unrelated vendors.

Measured cost of getting this wrong: `WHERE description LIKE '%SELECT%' AND
transaction_type='debit'` returns ₹1,394,994,707 over 7,854 rows. The correct answer for
Selection Mobile alone is ₹221,747,874 over 790 rows. **A naive filter overstates by 6.3x**
and states it with full confidence.

### 3. Alias spellings of one vendor

The same counterparty appears under several spellings, so canonicalisation is testable:

| Canonical | Spellings in the data |
|---|---|
| RELIANCE DIGITAL RETAIL LTD | `RELIANCE DIGITAL`, `RELIANCEDIGITAL RETAIL LTD` |
| TATA CONSULTANCY SERVICES LTD | `TATA CONSULTANCY`, `TCS LIMITED` |
| BLUE DART EXPRESS LIMITED | `BLUE DART`, `BLUEDART EXPRESS` |
| AMAZON SELLER SERVICES PVT LTD | `AMAZON SELLER SERV`, `AMAZON WEB SERVICES` |
| INFOSYS LIMITED | `INFOSYS`, `INFOSYS LTD` |

Person names also vary in case (`ritu verma`, `Ritu Verma`, `RITU VERMA`).

### 4. Reconciliation, since the schema has no status column

There is no `recon_status` column, so a definition has to be derived. Two signals exist:

- **Matched pair — 27,448 rows (13,724 pairs).** An internal transfer written as two
  transactions: a debit from one account and a credit into another, sharing an identical
  `utr_number` **and** `transaction_reference_id`, with the same amount, minutes apart.
  Verified: 100% of the 13,721 UTR values that appear on exactly two rows are a valid
  opposite-direction, equal-amount, cross-account pair.
- **Matched by reference — 15,499 rows.** Inward collections carrying a Bajaj Finance loan
  reference in the narration, format `ZBFLCTP` + 3 alphanumerics + `PBL` + 8 digits, e.g.
  `ZBFLCTP2Y5PBL28537746`.
- **Unmatched — 50,097 rows (50.1%).** Neither signal.
- **Not applicable — 6,956 rows.** Bank charges, which have no counterparty.

### 5. `utr_number` reproduces the sample's deterministic encryption

All 53,039 non-null UTRs share a fixed 20-character base64 prefix
(`jhI5nAdyb1qOEjmcB3Jv`), matching the 21-character shared prefix observed across every
UTR in the schema document's sample rows. Lengths are 56, 60 or 64 characters, as in the
sample.

The encryption is **deterministic**: the same plaintext always produces the same
ciphertext. That is what makes reconciliation by UTR possible, and it means an encrypted
column *can* be searched — encrypt the search term, then `WHERE utr_number = ?`. Verify
this against TBX's real encryption before relying on it. (A fixed prefix across all rows
is a genuine weakness in production, but that is not in hackathon scope.)

### 6. Amounts are always positive; direction lives in `transaction_type`

Net spend is:

```sql
SUM(CASE WHEN transaction_type = 'debit' THEN transaction_amount ELSE -transaction_amount END)
```

A plain `SUM(transaction_amount)` is wrong. With a 66,162 / 33,838 debit-credit split the
error is large and looks plausible.

`available_balance` on each account is the exact net of that account's transactions
(credits minus debits), so balances reconcile to the ledger. Many are negative, matching
the sign convention in the sample data.

### 7. Missing values

- 8,318 transactions (8.3%) have a NULL `transaction_reference_id`, concentrated in
  `IMPS OW` — matching the sample, where an `IMPS OW` row had no reference.
- 46,961 transactions (47.0%) have a NULL `utr_number`. UPI, `NEFT/`, `IMPS OW`,
  `IMPS/P2A` and `R/` rows never carry one.

Any question filtering on a reference has to handle NULL rather than dropping rows silently.

### 8. Planted anomalies

56 transactions are 9x to 38x their vendor's usual amount. Largest: ₹43,731,402 to
Dentsu Aegis Network India on 2026-07-10, against a median of ₹77,548 — 564x. These
support the brief's bonus "anomaly callouts" item. They are flagged `is_anomaly=1` in
`truth/transaction_truth.csv`, so a detector can be scored.

### 9. Optional defects (`--dirty`)

Off by default. Reproduces the two real defects found in the schema document's own sample rows:

- one transaction whose `transaction_id` is a malformed 31-character UUID with 4 groups
  instead of 5, which `VARCHAR(36)` accepts silently;
- four accounts whose `entity_id` reuses another row's `account_id`, so the two ID spaces
  are not disjoint.

## The answer key — `truth/`

**Never let the assistant read these.** They are for scoring only.

| File | Contents |
|---|---|
| `transaction_truth.csv` | Per transaction: true `counterparty_id`, `counterparty_name`, `rail`, `category`, `loan_ref`, `recon_status`, `recon_match_id`, `is_anomaly` |
| `counterparty.csv` | 198 counterparties with canonical name, category, and every alias |
| `entity.csv` | 48 entity names |
| `answer_key.json` | 20 questions with computed correct answers |

`transaction_truth.csv` lets you measure your parser directly: run your extractor over
`description`, join on `transaction_id`, and report counterparty-match accuracy. That
number goes in your deck against the 30% accuracy-and-grounding criterion and the bonus
"accuracy against a sample question set" item.

`answer_key.json` covers 5 plain lookups, 5 guardrail questions that **must be refused or
clarified**, 3 derived-category questions, 2 definitional, 2 rankings, 1 multi-turn
follow-up, 1 collision trap and 1 anomaly.

The five guardrail questions matter most, because the brief scores hallucination
guardrails explicitly:

| Question | Required behaviour |
|---|---|
| "How much did we spend on logistics in November 2024?" | Say there is no data — the window starts 2025-01-01 |
| "How much did we pay Acme Corporation last quarter?" | Say no such counterparty exists |
| "What is the GST component of our March 2026 invoices?" | Refuse — no tax or invoice data exists |
| "How much did we spend on Selection?" | Ask which of the eight — do not merge or guess |
| "What will we spend next month?" | Refuse — no forecast data |

## Known limitations

- **`category` is synthetic.** It exists only in `truth/`, never in the three tables,
  because the real schema has no category column. Category questions are answerable only
  by deriving category from the counterparty. If your assistant cannot, the correct
  behaviour is to say so.
- **The RTGS narration format is extrapolated**, not observed. The schema document's ten
  sample rows contain no RTGS transaction, so its format is modelled on the `NEFT  - ` form.
  The other nine formats are copied from real sample rows.
- **Account-number lengths are realistic per bank** (11 to 16 digits), whereas all ten
  sample rows used 14 digits regardless of bank. Realism was preferred; all values fit
  `VARCHAR(20)`.
- **43 entities appear, not 48.** Accounts are assigned to entities at random, so five
  entities ended up with no account. `truth/entity.csv` lists all 48.
- **The last day is partial and runs to 23:46 on 2026-09-05**, slightly ahead of a
  mid-morning wall clock. Harmless for month-level aggregation.
- **`schema.sql` changes `transaction_date` from `TIMESTAMP(6)` to `DATETIME(6)`.** MySQL
  converts `TIMESTAMP` to UTC on write and back to the session timezone on read, so a
  session-timezone mismatch silently moves month-boundary transactions into the wrong
  month. If you must keep `TIMESTAMP`, pin `SET time_zone = '+05:30';` on every connection.
- **The data is synthetic.** When the organisers ship the real starter dataset, treat this
  as a development and test fixture, not a substitute.
