# Finassist — a finance assistant that will not make a number up

**TBX problem statement · Bessemer Tech Catalyst, Bengaluru, 5 September 2026**

Ask about your transaction data in plain English. Get an answer, the rows behind it, the SQL
that produced it, and a CSV export.

> **SQL computes. The model only reads the answer out loud — and a validator checks every
> digit against a query result before it reaches you.**

---

## Run it

Prereqs: a running MySQL 8+, and `pip install -r requirements.txt` (just `PyMySQL`).

```bash
# 1. Point .env at your MySQL and create the database
cp .env .env.local            # edit MYSQL_PASSWORD etc.
mysql -u root -p -e "CREATE DATABASE IF NOT EXISTS finance CHARACTER SET utf8mb4;"

# 2. Generate + load the dataset (writes CSVs, seed SQL, and loads into MySQL)
python generate_dataset.py                       # 100,000 transactions (default)

# 3. Build the derived tables (counterparty, transaction_enriched) — ~10 s
python -m finassist.enrich

# 4. Start the assistant
python -m api.server                             # http://localhost:8720
```

Open the URL and ask a question.

<details><summary>A bigger dataset, or dirty rows</summary>

```bash
python generate_dataset.py --transactions 500000  # bigger
python generate_dataset.py --dirty                # inject the malformed rows found in the real sample
python generate_dataset.py --no-load              # write files only, don't touch MySQL
python -m finassist.enrich
```

The generator is seeded, so a rerun reproduces the same data byte for byte. See
[`data/DATASET.md`](data/DATASET.md) for what is in it and which traps are planted on purpose.
</details>

## What it does

| Requirement from the brief | How it is met |
|---|---|
| Natural-language questions | Keyword rules cover the common shapes; a small model handles the rest. 13 intents. |
| Grounded retrieval | Every figure comes from a parameterised SQL query over the dataset. No generated SQL. |
| Accurate computation | Filtering, grouping and aggregation happen in SQL. The model receives finished numbers. |
| Verifiable answers | Every answer ships with a breakdown table, an evidence ledger, and the exact SQL and parameters. |
| Hallucination guardrails | Five guards run *before* any number is computed, plus a numeric validator on the model's output. |
| Lightweight model | 20/20 on the answer key with **zero model calls**. The model is optional throughout. |
| Multi-turn | The session carries the last counterparty, period and intent. "How does that compare to the month before?" stays scoped to the vendor you just asked about. |
| Explainability | The evidence ledger shows what was queried, with what parameters, and how many rows came back. |
| CSV export | Per turn, so an earlier answer's export link keeps working. |
| Confidence signalling | Ambiguous vendor names produce a clarification, not a guess. Derived fields carry a stated caveat. |
| Anomaly callouts | Payments more than 4 robust standard deviations above that counterparty's own median, in log space. |

## The three things that actually decide the score

### 1. The schema is missing most of what the brief asks for

The brief names transactions, vendor payouts, reconciliation status, a chart of accounts and a
vendor list. The schema has `bank`, `account`, `transaction`. Vendor identity, category and
reconciliation status exist nowhere but inside one free-text `description` column, in nine
different narration formats with the counterparty in a different position in each.

So the whole competition is the enrichment layer. `finassist/rails.py` parses it, once, at
ingestion. Afterwards every question is an indexed `GROUP BY`.

### 2. A naive vendor filter is wrong by 6.3x, confidently

Nine counterparties in the data contain the string `SELECT`, and they are different
businesses. Two shopping-mall names in the location suffix contain it too.

```
WHERE description LIKE '%SELECT%' AND transaction_type='debit'
  ->  Rs 1,394,994,707 over 7,854 rows

The correct answer for Selection Mobile alone
  ->  Rs   221,747,874 over   790 rows
```

`finassist/rails.py` splits the location off before matching and folds abbreviations with
length-guarded containment, never substring matching. Ask "how much did we spend on
Selection?" and the assistant lists all five matches and asks which one — it does not pick the
biggest and call it an answer.

### 3. "Last month" must mean the data's last month

The sample data in the schema document stops at 2026-06-24. Against a wall clock, "last month"
returns zero rows and a careless assistant reports a spend of zero. Every relative period here
is measured from `MAX(txn_date)`, and the coverage window is printed in the UI header.

## Guardrails, with the actual output

| Question | What it does |
|---|---|
| "How much did we spend on logistics in November 2024?" | *No data for November 2024. This dataset covers 2025-01-01 to 2026-09-05, so there are no transactions in that period.* |
| "How much did we pay Acme Corporation last quarter?" | *No counterparty matching "Acme Corporation" appears in the data.* |
| "How much did we spend on Selection?" | *"Selection" matches 5 different counterparties… Which one did you mean?* |
| "What is the GST component of our March 2026 invoices?" | *The data has no tax breakdown. It holds bank transactions only, with no invoice or line-item detail.* |
| "What will we spend next month?" | *The data ends at the last recorded transaction and contains no forecast.* |
| "Who is our largest customer?" | *The data does not label counterparties as customers or suppliers…* |

And the model's own output is validated. Click **⛔ Try to make it fabricate a number** in the
UI, or `POST /demo/fabrication` — a doctored draft goes through the same validator that gates
every reply, and you watch it get rejected. It runs offline with no model call, so it cannot
flake on stage.

## Layout

```
generate_dataset.py      seeded synthetic data matching the TBX schema
build_answer_key.py      computes the ground-truth answers
finassist/
  rails.py               narration parser (9 formats) + canonicalisation
  aliases.py             the acronym map a finance team owns
  enrich.py              builds counterparty + transaction_enriched
  resolve.py             dates and vendor names -> rows, deterministically
  intents.py             13 parameterised queries; the ONLY place a number is computed
  plan.py                question -> intent + slots (rules first, model second)
  narrate.py             the numeric validator + deterministic template
  engine.py              orchestration, guardrails, multi-turn session
api/server.py            stdlib HTTP server: chat UI + JSON API + CSV export
ui/index.html            self-contained chat page, no CDN
tests/
  eval_enrichment.py     grades the derived tables
  eval_answers.py        grades the assistant against the answer key
  make_samples.py        regenerates SAMPLE_ANSWERS.md
data/
  DATASET.md             what is in the data and which traps are deliberate
  truth/                 the answer key — the engine never reads this
```

## API

| | |
|---|---|
| `GET /` | the chat page |
| `GET /health`, `GET /stats` | dataset stats and coverage window |
| `POST /ask` | `{question, session_id}` → the full answer object |
